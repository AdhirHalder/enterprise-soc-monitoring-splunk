# Project Methodology

## 1. Overview

The project follows a practical SOC workflow combining security log ingestion, SIEM-based analysis, threat hunting, dashboard development, detection engineering, alerting, and MITRE ATT&CK mapping.

The implementation uses a controlled single-machine Windows 10/11 lab environment containing Splunk Enterprise, Splunk Universal Forwarder, XAMPP, and DVWA. BOTSv1, BOTSv2, and BOTSv3 provide historical security telemetry for threat hunting.

## 2. Log Ingestion Methodology

The Splunk Universal Forwarder is configured to monitor Apache access logs generated by the DVWA/XAMPP environment.

The monitored log source is:

`C:\xampp\apache\logs\access.log`

The events are assigned:

- Index: `dvwa`
- Sourcetype: `access_combined`

The Universal Forwarder forwards the events to the local Splunk Enterprise indexer through TCP port `9997`.

BOTSv1, BOTSv2, and BOTSv3 are used as pre-loaded datasets containing historical network, endpoint, database, identity, and cloud security telemetry.

## 3. Dashboard Development Methodology

Each dashboard follows a standardized development process.

### Step 1 — Sourcetype Exploration

Raw events and available fields are examined before developing detection queries.

Commands such as `head` and `fieldsummary` are used to understand the structure of the available data.

### Step 2 — SPL Query Development

Splunk Processing Language (SPL) queries are developed according to the structure and purpose of each data source.

Common SPL commands used include:

- `stats`
- `timechart`
- `eval`
- `rex`
- `spath`
- `mvexpand`

### Step 3 — Visualization Selection

Visualizations are selected according to the type of security data being analyzed.

Examples include:

- Pie charts for distributions
- Bar charts for rankings
- Line charts for time-series activity
- Tables for detailed security events and alerts

### Step 4 — Dashboard Panel Creation

Developed SPL queries are saved as dashboard panels in Splunk Web.

Panels are organized into themed dashboards according to the security domain being investigated.

### Step 5 — Finding Documentation

Important findings are documented from the dashboard analysis, including:

- Indicators of compromise (IOCs)
- Suspicious IP addresses
- Anomalous activity
- Event counts
- Attack patterns
- MITRE ATT&CK technique mappings

## 4. Threat Hunting Methodology

Threat hunting is performed across the BOTSv1, BOTSv2, and BOTSv3 datasets.

The investigation focuses on identifying suspicious activity across multiple security domains, including:

- Network security
- Endpoint security
- Authentication
- DNS
- Web applications
- Databases
- Cloud security
- Identity and access
- Lateral movement
- Data loss indicators
- Threat intelligence

The investigation uses SPL-based searches to identify anomalies, suspicious communication, attack patterns, and indicators of compromise.

## 5. Real-Time Attack Detection

The DVWA environment is used as a controlled live attack target.

Three attack scenarios are monitored:

1. Brute Force
2. SQL Injection
3. Cross-Site Scripting (XSS)

Security activity generated against DVWA is captured through Apache and DVWA-related logs and analyzed in Splunk.

## 6. Alerting Methodology

Three real-time Splunk alerts were configured for the DVWA monitoring component:

- Brute Force Attack
- SQL Injection Attack
- Cross-Site Scripting (XSS)

The alerts use defined detection conditions and throttling/suppression to reduce repeated alert generation.

Alert severity and notification actions are documented separately in the `alerts/` directory.

## 7. IOC Correlation

The project uses IOC correlation to connect suspicious indicators across security telemetry.

Examples of indicators considered during investigations include:

- Source IP addresses
- Destination IP addresses
- Domains
- User accounts
- Hostnames
- Suspicious URLs
- Attack payloads

Cross-source correlation helps provide additional context during security investigation.

## 8. MITRE ATT&CK Mapping

Detected activities are mapped to relevant MITRE ATT&CK tactics and techniques.

The mapping provides a structured way to document:

- Attack behavior
- Adversary techniques
- Detection coverage
- Threat investigation context

The complete mapping is maintained in:

`mitre/mitre-mapping.md`

## 9. Investigation and Analysis Workflow

The overall SOC investigation workflow is:

1. Collect security telemetry.
2. Index events in Splunk.
3. Explore available fields and sourcetypes.
4. Develop SPL searches.
5. Identify suspicious activity.
6. Correlate relevant indicators.
7. Visualize security events through dashboards.
8. Trigger configured detections and alerts.
9. Investigate the observed activity.
10. Document findings.
11. Map relevant activity to MITRE ATT&CK.

## 10. Controlled Lab Environment

The project is implemented as a controlled cybersecurity lab.

DVWA is intentionally vulnerable and is used only for authorized attack simulation and detection testing.

The BOTSv1, BOTSv2, and BOTSv3 datasets provide historical security events for analysis and threat hunting.
